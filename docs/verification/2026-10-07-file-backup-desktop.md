## 文件选择、定位与生命周期

驱动 [verify-notes-files.cjs](../../scripts/verify-notes-files.cjs) 先校验原生存储路径，再按 PID/可执行路径/SHA 验证 QA 对话框归属。只选项目夹具，未使用全局键盘输入或操作其他应用窗口。普通中文、中文空格、中文逗号空格三类文件分别使用真实 Windows 选择对话框加入，另取消一次；原生回读顺序和完整路径一致。

定位改用 `SHParseDisplayName` / `SHOpenFolderAndSelectItems`，COM 与 PIDL 按作用域释放；目录保留打开文件夹的行为。依据 [Microsoft Shell API](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shopenfolderandselectitems)。验收通过 Shell COM 明确枚举视图及 SelectedItems，逐一确认准确选中的三个文件；不是只检查 spawn 成功。旧单参数 `/select,<path>` 方式以 Node Windows 参数转义模拟调用逗号空格夹具，进程退出 1、选择仍停留在原文件；未将此模拟说成重新启动旧版完整应用。

文件临时改名后，定位显示“文件已不存在或无法访问，引用仍保留”，三项引用保留。恢复文件后移除其中一个引用、删除并恢复便签，三份外部文件逐字节保持合成原内容。最新报告 `reports/files-1791370183716.json`，逐步骤记录 `files-progress-1791370169989.json`；前一 scope 报告 `files-1791369471911.json` 仍保留。

检查还发现对话框与自动隐藏的竞态：原先没有绑定主窗口，选文件前的仅标题草稿会因失焦隐藏触发提前保存提示；仅绑定父窗口仍不足。便签、备份和目录选择均绑定主窗口，并在真实对话框存活期间保护自动隐藏；所属前台弹窗也按 `GA_ROOTOWNER` 判断。此 Release 中对话框打开时主窗口保持可见，没有再产生仅标题提前保存提示。全应用唯一门闸的增强已复验：第一个对话框存活时，第二个原生选择请求返回 `notes.busy`，随后正常选择/取消仍可连续执行。保护由真实回调持有，IPC 超时不提前释放；超时满时长场景尚未另做桌面检查。

驱动自身的失败单独处理：现代保存对话框的文件名 Edit ID 与旧选择器不同；COM 集合使用显式索引枚举；子进程 stdout 强制 UTF-8，否则准确中文路径会被误解码而断言失败。这些失败不能全部归为产品缺陷。

## 目录迁移、源路由故障与原生重启

[verify-notes-storage.cjs](../../scripts/verify-notes-storage.cjs) 通过真实「更改」文件夹对话框及前端保存屏障操作；[qa-storage-fixture.py](../../scripts/qa-storage-fixture.py) 将数据库故障注入限定于独立 QA 默认库和项目合成夹具目录。测试包括中文、空格、逗号目标路径，活动/归档/最近删除便签及外部文件引用。没有借助强制结束进程充当重启验收。

默认 Release 报告 `reports/storage-1791372181451.json` 通过以下检查：

- 目标已有便签时拒绝覆盖，目标正文和原有设置逐项不变，源连接/epoch 不变。
- 源库 `storage_path` 写入触发器故障发生在目标联合事务提交之后；旧连接/epoch 保持，目标保留暂存凭据，源剪贴板合成记录未复制到目标。
- 失败期间在源库新编辑便签，移除故障后再选相同目标，重试成功带上新编辑。目标原有 `qa_existing_target` 设置保留，便签创建请求身份/哈希、引用 ID/路径和归档/删除状态保持。
- 切换后旧 epoch 读取与保存均拒绝，页面重新加载当前摘要。目录选择后的失败提示为完整中文；新增中英文三项路径/冲突/迁移错误文案，英文尚待桌面复验。

此默认 `native-release-storage` / `frontend-storage` EXE **46,118,912** 字节，SHA `e8bf2c39c3bb81576385e260821176945076e176ab96c3f7dc52062ef29d244e`，构建 60 秒。与上一默认 QA 产物相差 -1,024 字节，混合了文案与重启代码变化，不归为独立优化收益，也不是生产安装包。最新完整 Rust **120 通过、2 个基准忽略**，15.37 秒；前端 **38/38**、类型检查、完整 lint 和生产前端构建通过。诊断版本先行报告 `storage-1791371927175.json` 保留，默认版本另行复验。

实际验收发现并修复重启缺陷：旧 Windows 路径在文件夹选择、迁移和新草稿保存之后，保存确认/后台排空/`ExitRequested approved=true` 均发生，却没有 `RunEvent::Exit`，进程未替换；失败报告 `storage-1791371022966.json` 及 `storage-1791371618589.json` 保留，不能按“已保存”宣称重启成功。无待保存稿的重启曾成功。现在 Windows 在自有保存交接、后台排空、密码箱锁定和敏感剪贴板清理之后，把 Tauri `AppHandle::restart` 排入主线程，利用其主线程直接清理/重启路径；其他平台保留 `request_restart`。API 行为核对锁定 Tauri 2.11.1 本地源码及[官方源码](https://github.com/tauri-apps/tauri/blob/tauri-v2.11.1/crates/tauri/src/app.rs)。尚未将原因扩大断言为所有版本的 Tauri 缺陷，也没有升级工具链绕开问题。

诊断阶段日志仅包含固定阶段名/批准布尔值，不记录正文、密码、ID 或路径，默认 Release 不启用日志。卡住的旧 QA 会话先核对协调器无 pending、选中正文/版本与隔离数据库一致，再重载测试界面并执行 QA 更新；这种恢复操作明确不计为原生重启成功。驱动另修正 Python 管道 UTF-8、Windows `\\?\` 路径前缀与 UIAutomation 程序集依赖问题；选择/取消无需加载 UIAutomation，只有 inspect 使用它。
