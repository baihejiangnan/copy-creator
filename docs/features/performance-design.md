## 1. 目标与边界

在保留字体效果、美化、图片预览、数据保留和全部已有功能的前提下，减少发布资源、无效请求、隐藏工作、重复计算及数据库长持锁。优化可以独立交付，不以加入便签为前提；便签也不等待全部优化完成。

共用合同 S-01～S-04 由先实施的任务完成一次：保存屏障、连接配置/迁移、存储身份、有界后台 DB 调度。便签自身必须可靠；现有热点经实测阻塞保存或交互预算后才成为其前置，不把全应用重构当作首发门槛。

2026-10-07 第二批已接入应用级保存屏障和原生排空，整轮剪贴板文件处理/采集、清理、同步变更和已接受密码箱异步任务纳入交接；翻译网络返回持锁校验原 epoch，避免跨目录写入。便签协调器设 4 个 dirty 会话及原始字段/快照预留预算；这些是可靠性边界，不能当作 CPU、内存、尾延迟优化成绩。当前中间构建仅验证可构建，不能替代 R0/R1 字体独立对照或最终 R2 验收；见[保存交接验证](../verification/2026-10-07-save-handoff.md)。

第三批接入备份预检/累计预算/精确有界序列化、原缓冲加解密、共享暂存及 2 个后台槽，图片准备移出锁；当批 108 项 Rust 测试通过。随后容量台账、图片/查询和分包已经接入；近上限备份 Release 峰值/锁时长、全应用运行与编译配置实验继续，不能将静态改造当作 O 整体验收通过。历史边界见[第三批验证](../verification/2026-10-07-backup-relocation.md)。

优化候选按三类处理：有静态证据的发布资源；源码确认的重复/阻塞路径；需要 Release 实测才能决定的格式、调度、索引或编译配置。每次仅改变可解释的一组因素，报告收益和回归。没有实测时不承诺 CPU、内存或延迟降低幅度。

### 优先处理：共享可靠性与阻塞边界（按 S/O 分工）

| 确认事实 | 建议 | 验收重点 |
| --- | --- | --- |
| 多个 SQLite 命令是普通同步 Tauri command，例如 `db.rs:803` 的列表查询 | 重查询、锁等待、文件 I/O 进入有界后台 blocking executor；保留现有连接，逐项迁移热点命令 | 主线程不执行这些重操作；记录排队、持锁和 SQL 时间 |
| 托盘退出直接 `app.exit(0)`，设置页可以重启 | 统一退出/重启保存交接，再结束进程 | 所有待保存便签获得提交确认；失败时草稿保留且用户能重试 |
| 存储切换创建和配置连接的代码与启动路径分开 | 统一连接配置和版本迁移；给便签定义明确的迁移合同 | 新库有完整表、索引和 PRAGMA；迁移失败不切换连接 |
| 列表请求返回后直接写入 store，没有查询代次校验 | 使用 `queryKey + generation`；同查询的分页单飞 | 旧查询响应不能覆盖新查询，失败请求不能清掉新请求状态 |
| 全局快捷键 handler 忽略具体按键，统一切窗 | 开放全局快捷捕获前建立按动作分发的路由，不作为仅有页内便签的首发前置 | 新建便签是显示并聚焦，不会变成隐藏，也不清空草稿 |

Tauri 官方说明普通同步命令的执行线程与异步命令不同；这里的目标是把阻塞工作交给后台执行，而不是仅在函数签名前加 `async`。参见 [Tauri 命令线程说明](https://v2.tauri.app/develop/calling-rust/#async-commands)。

`spawn_blocking` 解决线程阻塞的位置，不解决全量扫描或同一数据库锁的争用。执行器要限制在途任务和队列长度，并合并可替代的查询；不能每次输入都创建一个无界阻塞任务。

### 已有功能中回报较明确的性能优化

1. **减少发布资源并保留字体效果。** 从发布集合排除 37 个未引用字体，保留 PingFang 300/400/500/600 与品牌 SF Pro 字体；再评估完整字符集的 WOFF2 压缩。系统字体继续作为缺字或加载失败的后备，不作为本轮主字体替换方案。
2. **修复图片缓存的条件性重复请求。** `ImageThumb.tsx:43` 的 `visible` 一旦为 true 不再恢复，而缓存只保留 80 条。超过 80 个曾进入观察范围且继续挂载的图片，可能在淘汰后互相触发重请求。这个链路可从代码推导，但尚未运行复现；先用合成图片确认静止后的请求，再改为当前可见性跟踪、同 ID 请求合并与缓存/组件引用的合理解耦。不能只扩大缓存掩盖问题。
3. **把剪贴板容量统计移出每次插入的全量路径。** `clipboard.rs:1106` 调用容量清理，`db.rs:349–416` 读取历史正文，并在锁内统计图片文件尺寸。持久化内容字节数、图片资产尺寸和引用数，在事务中增量维护；完整核对和物理文件清理放后台。不要仅把原来的全量扫描挪到另一个线程。
4. **列表只读摘要。** 当前 SQL 读取全文，再在 Rust 截成 600 字；每页还读全部 API 标签。保存时维护摘要/长度，列表只请求必要字段，标签 JOIN 当前页；全文保留独立读取接口。受保护内容继续使用脱敏摘要。
5. **拆分主窗口与轮盘入口。** `main.tsx` 按窗口类型动态加载，便签、翻译、密码箱和设置页使用 `React.lazy`，页面 CSS 随模块加载。保留必要的全局会话逻辑；静态依赖仍在时，不能声称对应模块已经完全拆开。React 支持首次渲染时再加载组件代码，见 [React lazy](https://react.dev/reference/react/lazy)。
6. **稳定分页与渲染。** 当前 offset 来自会被实时事件改动的 `records.length`；改用 `(created_at,id)` 游标及 ID 去重，并校验事件是否属于当前分类/查询。新项插入使所有旧卡片的 `index` 改变；限制入场动画条数与延迟，避免破坏全部卡片的 props 稳定性。

第 3 项的统计应保留已有收藏和受保护 API Key 的保护规则。便签所占空间可以显示在总统计中，但不能顺带加入剪贴板的自动淘汰集合。

### 字体、美化与热点的具体执行方案

**字体采用两步优化。** 第一步只改变发布边界：将 37 个未引用字体移到构建范围外的源资产目录；当前使用的 5 个文件仍提供给 CSS，已有字号、字重、字距和行高不变。正式构建应检查字体清单，防止后续又把素材全集复制进 `dist`。本轮实验已核验这个步骤的静态体积收益。

第二步把当前 5 个字体转换为 WOFF2，保留完整 glyph、字符映射、布局、字距和 hinting 数据；不先做“只保留界面固定文案”的子集，因为剪贴板、便签、网址和文件名都包含用户任意输入。WOFF2 的转换保持字体功能与字形保真，解码后的二进制不必与原文件逐字节相同，参见 [W3C WOFF2](https://www.w3.org/TR/WOFF2/)。转换后需检查字符覆盖与度量，并做实际 WebView2 对照；完整集合压缩和真实渲染/解码成本已在隔离实验测得，原生匹配控制及采用判断仍以[实际字体记录](../verification/2026-10-08-font-woff2.md)为准，不能由字体原始文件减少推导安装包或内存收益。

正式资源组织建议：原始字体与未使用素材放在前端构建范围之外；分发字体放在 `src/assets/fonts/`，CSS 使用模块相对 URL，让 Vite 跟踪引用和生成指纹。转换验证通过的发行版本避免同时携带同字重的 TTF/OTF 与 WOFF2。压缩工具属于构建工具，不作为客户端常驻依赖；WOFF2 也不能被直接算成解码后内存下降。

**美化优化发生在不可见工作中。** 保留现有毛玻璃、阴影、圆角、悬停预览、浅深色主题与视觉反馈。卡片入场动画只在新项出现时触发，保留节奏但限制错峰总时长；新剪贴板项不能让所有旧卡片重新入场。暂停隐藏窗口和离屏区域的无效工作。涉及模糊层合并时，先确认它们覆盖范围、层级与透明结果相同，再去掉重复处理；不得为了帧率直接关掉全局美化。

**图片修复保留预览能力。** Observer 跟踪当前是否进入观察范围，离开后不再补缓存；使用 `inFlight[id]` 合并同一图片请求。队列中尚未执行且已无人需要的任务可丢弃；缓存按数量与字节有界管理，当前可见引用优先保留。当前屏幕的工作集超过缓存预算时，应采用有界挂载或临时可见引用管理，不能让淘汰与补入重新形成循环。需要时再换成可回收的 Blob URL，确认引用计数和 revoke 时机后采用，避免预览突然空白。

**容量统计做成共享基础能力，生命周期保持独立。** 插入、删除和修改内容时在事务中维护字节数及图片资产引用；图片生成时记录文件与缩略图实际尺寸，重复资产只计算一次。短语、便签和密码箱空间分别统计，界面可显示总占用，但现有剪贴板清理只处理原有允许清理的记录。超过阈值时合并清理工作，后台一次处理一批并让出执行机会；回收前按相同资产版本/引用状态复核，避免与新写入竞争误删文件。统计修复、迁移与导入统一更新这些元数据。

**分包优化针对启动和解析，不宣称总代码凭空变少。** 首屏只加载当前入口、基础样式与必要会话控制；便签、翻译、密码箱页面、设置和关于内容按访问加载。现有更新检查保持一次会话启动语义，详情 UI 可延迟加载。模块切换前预取只响应明确用户意图，避免启动后立刻预取所有页面抵消收益。总 chunks、首屏字节和首次进入延迟分别报告。

**搜索按数据保护边界分别优化。** 普通剪贴板与便签共享查询代次、分页和输入去抖的模式。密码箱当前每次查询读取并解密所有记录（`vault.rs:list_vault_entries`）；只有测得其为瓶颈时，才增加解锁会话内的最小搜索字段/摘要缓存，编辑后失效、锁定后清空，每次命令仍校验权限。不得用明文磁盘索引或放宽锁定规则来换速度，也不因便签接入强行重写密码箱。

## 6. 实施顺序与验收

建议先 O-01 固定基线；O-02 资源精简与 O-03/O-04 小范围修复可独立进行，再按测量推进 O-05/O-06 和 O-07/O-08。WOFF2 未通过验证可先保留原 5 字体；不要等待所有实验或 O-09 候选才交付已经验证的改进。

保留 R0 当前版、R1 优化版、R2 加便签版。R1−R0 回答优化收益，R2−R1 回答便签增量，R2−R0 回答最终整体变化；如便签先接入，保留相应独立改动的可重建快照，不能把功能变化归为优化收益。

采用独立合成数据与同一参考 Windows 11 设备的 Release；空库、2,000 剪贴板 + 2,000 便签（常规正文 1–4 KiB）、10k/50k 压力、100–200 图片、256 KiB 单篇、近 74 MiB 备份分别测量。冷启动至少 30 次，预热操作至少 100 次，报告 P50/P95、必要 P99、样本量与波动。预算和视觉/全部功能清单参见 [便签设计 §7/§9](notes-design.md)。

输入延迟明确为输入事件至对应内容呈现，首次进入为动作至可输入，保存计时从提交开始并另报防抖等待；不能用函数执行时间代替用户等待。记录 IPC 数量/字节、长任务、React commit、队列/锁/SQL 分段时间和进程树 private bytes/working set，日志不记录正文、Key 或完整路径。

O 的完成条件：发布体积实测减小，指定热点有实测改善，常规剪贴板/图片/切窗/输入不出现超出波动的回退，字体、美化、预览和全部已有功能回归通过。不以删功能、减少数据、去掉视觉效果或降低持久性来达标。N 的增量预算单独验收，不能替代原 PRD 的整体目标。
